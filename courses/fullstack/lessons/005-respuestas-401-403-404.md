La implementación de un sistema de autorización robusto, como el que hemos construido con roles, permisos y middleware, requiere una comunicación precisa con el cliente cuando una solicitud falla. No basta con denegar el acceso; es fundamental indicar la razón del fallo de manera consistente y segura. Una respuesta HTTP incorrecta puede confundir al cliente o, peor aún, filtrar información sensible sobre la estructura interna de la aplicación o la existencia de recursos. Por ello, es crucial distinguir cuándo responder con un 401 Unauthorized, un 403 Forbidden o un 404 Not Found.

### Problema: Comunicación ambigua de fallos de acceso

Cuando un usuario intenta acceder a un recurso o realizar una acción sin la debida autorización o autenticación, el servidor debe responder con un código de estado HTTP que refleje la naturaleza exacta del problema. Una respuesta genérica, como un 400 Bad Request, no proporciona suficiente información. Por otro lado, una respuesta demasiado específica podría revelar detalles que un atacante podría explotar. El desafío es encontrar el equilibrio entre claridad para el cliente legítimo y seguridad frente a actores maliciosos.

Consideremos una aplicación de gestión de documentos donde los usuarios pueden crear, leer, actualizar y eliminar sus propios documentos, y los administradores pueden gestionar todos los documentos. Un usuario intenta acceder a un documento. Las posibles situaciones son:

1.  **El usuario no ha iniciado sesión.** No hay credenciales de autenticación válidas en la solicitud.
2.  **El usuario ha iniciado sesión, pero no tiene permiso para acceder a ese documento.** Por ejemplo, intenta ver un documento privado de otro usuario o un documento de administración.
3.  **El documento solicitado no existe.**

Cada uno de estos escenarios requiere una respuesta HTTP distinta para ser manejado correctamente por el cliente y para mantener la seguridad del sistema.

### Flujo de decisión para códigos de estado

Para responder de forma consistente y segura, se puede seguir el siguiente flujo de decisión:

1.  **¿La solicitud incluye credenciales de autenticación válidas?**
    *   Si **no** hay credenciales (por ejemplo, no hay token de sesión o cookie), o si las credenciales son inválidas o han expirado, la respuesta debe ser `401 Unauthorized`. Este código indica que la solicitud no ha sido aplicada porque carece de credenciales de autenticación válidas para el recurso objetivo. A menudo, se acompaña de un encabezado `WWW-Authenticate` para indicar cómo autenticarse.
    *   Si **sí** hay credenciales válidas, se procede al siguiente paso.

2.  **¿El usuario autenticado tiene permiso para realizar la acción solicitada sobre el recurso?**
    *   Si **no** tiene permiso (por ejemplo, un usuario normal intenta acceder a una ruta de administración, o intenta modificar un recurso que no le pertenece), la respuesta debe ser `403 Forbidden`. Este código indica que el servidor entiende la solicitud pero se niega a autorizarla. La autenticación fue exitosa, pero la autorización falló. Es importante destacar que el servidor *sabe* que el recurso existe, pero el usuario no tiene acceso.
    *   Si **sí** tiene permiso, se procede al siguiente paso.

3.  **¿El recurso solicitado existe?**
    *   Si **no** existe, la respuesta debe ser `404 Not Found`. Este código indica que el servidor no pudo encontrar el recurso solicitado. Es crucial que, en algunos casos, se utilice `404 Not Found` incluso cuando el recurso *podría* existir, pero el usuario no tiene permiso para saberlo. Esto se hace para evitar la enumeración de recursos. Por ejemplo, si un usuario no autorizado intenta acceder a `GET /users/123`, y el usuario `123` es un usuario real pero privado, responder con `404` en lugar de `403` evita confirmar la existencia del usuario `123` a un atacante.
    *   Si **sí** existe y el usuario tiene permiso, la solicitud se procesa normalmente (por ejemplo, `200 OK`, `201 Created`, etc.).

### Ejemplo de código mínimo (Node.js con Express)

Consideremos un middleware de autorización que ya verifica la autenticación y los permisos. Podemos refinar las respuestas de error.

```javascript
// authMiddleware.js
const jwt = require('jsonwebtoken');

const authenticate = (req, res, next) => {
    const authHeader = req.headers.authorization;
    if (!authHeader) {
        return res.status(401).json({ message: 'Autenticación requerida' });
    }

    const token = authHeader.split(' ')[1];
    if (!token) {
        return res.status(401).json({ message: 'Token de autenticación ausente' });
    }

    try {
        const decoded = jwt.verify(token, process.env.JWT_SECRET);
        req.user = decoded;
        next();
    } catch (error) {
        return res.status(401).json({ message: 'Token de autenticación inválido o expirado' });
    }
};

const authorize = (roles = []) => {
    return (req, res, next) => {
        if (!req.user) {
            // Esto no debería ocurrir si authenticate se ejecuta primero
            return res.status(401).json({ message: 'Usuario no autenticado' });
        }
        if (roles.length && !roles.includes(req.user.role)) {
            return res.status(403).json({ message: 'Acceso denegado: Permisos insuficientes' });
        }
        next();
    };
};

const checkOwnership = (model) => {
    return async (req, res, next) => {
        const resourceId = req.params.id;
        const resource = await model.findById(resourceId);

        if (!resource) {
            // Ocultar la existencia del recurso si el usuario no tiene permiso para verlo
            return res.status(404).json({ message: 'Recurso no encontrado' });
        }

        // Asumiendo que el recurso tiene un campo 'owner' o 'userId'
        if (resource.ownerId.toString() !== req.user.id) {
            // Si el usuario no es el propietario, responder con 404 para no filtrar si existe
            // o 403 si la existencia no es sensible y queremos indicar falta de permiso
            // Para este ejemplo, elegimos 404 para mayor seguridad.
            return res.status(404).json({ message: 'Recurso no encontrado' });
        }
        req.resource = resource;
        next();
    };
};

module.exports = { authenticate, authorize, checkOwnership };
```

```javascript
// routes/documentRoutes.js
const express = require('express');
const router = express.Router();
const Document = require('../models/Document'); // Suponiendo un modelo Mongoose
const { authenticate, authorize, checkOwnership } = require('../middleware/authMiddleware');

// Ruta para obtener todos los documentos (públicos o propios)
router.get('/documents', authenticate, async (req, res) => {
    // Lógica para filtrar documentos por usuario o mostrar públicos
    const documents = await Document.find({ ownerId: req.user.id }); // Ejemplo: solo propios
    res.json(documents);
});

// Ruta para obtener un documento específico por ID
router.get('/documents/:id', authenticate, async (req, res) => {
    const document = await Document.findById(req.params.id);
    if (!document) {
        return res.status(404).json({ message: 'Documento no encontrado' });
    }
    // Si el documento es privado y el usuario no es el propietario, responder 404
    if (document.isPrivate && document.ownerId.toString() !== req.user.id) {
        return res.status(404).json({ message: 'Documento no encontrado' });
    }
    res.json(document);
});

// Ruta para actualizar un documento (solo propietario)
router.put('/documents/:id', authenticate, checkOwnership(Document), async (req, res) => {
    const { title, content } = req.body;
    req.resource.title = title || req.resource.title;
    req.resource.content = content || req.resource.content;
    await req.resource.save();
    res.json(req.resource);
});

// Ruta para eliminar un documento (solo propietario)
router.delete('/documents/:id', authenticate, checkOwnership(Document), async (req, res) => {
    await req.resource.remove();
    res.status(204).send(); // No Content
});

// Ruta de administración (solo administradores)
router.get('/admin/documents', authenticate, authorize(['admin']), async (req, res) => {
    const allDocuments = await Document.find();
    res.json(allDocuments);
});

module.exports = router;
```

En este ejemplo, `authenticate` maneja el `401`. `authorize` maneja el `403` para roles. `checkOwnership` y las rutas individuales manejan el `404` cuando un recurso no existe o cuando un usuario no autorizado intenta acceder a un recurso que no le pertenece, ocultando su existencia.

### Práctica: Refinar respuestas de error

Modifique una de sus rutas existentes que requiera autenticación y autorización. Asegúrese de que:

1.  Si no se proporciona un token de autenticación o es inválido, la respuesta sea `401 Unauthorized`.
2.  Si el usuario está autenticado pero no tiene los permisos necesarios para la acción o el recurso (por ejemplo, intenta acceder a un recurso de otro usuario o a una ruta de administrador sin serlo), la respuesta sea `403 Forbidden`.
3.  Si el recurso solicitado no existe, o si existe pero el usuario no tiene permiso para saber de su existencia (y se desea ocultarla), la respuesta sea `404 Not Found`.

Utilice el flujo de decisión y los ejemplos de código como guía para implementar estas respuestas de manera consistente.

### Comprobaciones

1.  Un usuario sin token de sesión intenta acceder a `GET /api/documentos/123`. ¿Qué código de estado HTTP debería recibir y por qué?
    *   **Respuesta:** Debería recibir `401 Unauthorized`. La razón es que la solicitud carece de credenciales de autenticación válidas, lo que indica un fallo en la autenticación.

2.  Un usuario autenticado con rol 'editor' intenta acceder a `GET /api/admin/usuarios`. La ruta `/api/admin/usuarios` solo es accesible para usuarios con rol 'admin'. ¿Qué código de estado HTTP debería recibir y por qué?
    *   **Respuesta:** Debería recibir `403 Forbidden`. La razón es que el usuario está autenticado, pero no tiene los permisos necesarios (rol 'admin') para acceder a ese recurso o realizar esa acción. El servidor entiende la solicitud pero se niega a autorizarla.

La correcta elección de códigos de estado HTTP es una parte integral de la seguridad y usabilidad de una API. Permite a los clientes reaccionar adecuadamente a los fallos y protege la información sensible del servidor.
